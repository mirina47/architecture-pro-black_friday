### 2. Стратегии шардирования

### Коллекция orders
**Шард-ключ**: ```{ client_id: 1, _id: 1 }```

**Стратегия**: Диапазонное шардирование

**Обоснование**:
- Ключ client_id обеспечивает быструю работу таких запросов, как поиск истории заказов конкретного клиента. Добавление _id помогает равномерно распределить заказы очень активных клиентов.
- Диапазонное шардирование подходит, так как заказы относятся к последовательным данным. Также в плюсах легкая реализуемость и быстрый поиск информации по сравнению с хэшированием.

**Пример команды**: 
```
sh.shardCollection("db.orders", { client_id: 1, _id: 1 })
```

### Коллекция products
**Шард-ключ**: ```{ "_id" : "hashed" }```

**Стратегия**: Хэшированное шардирование

**Обоснование**:
- Ключ _id уникален, поэтому может обеспечить хорошее распределение данных
- Хэшированное шардирование подходит, так как товары в магазине крайне важно распределять равномерно. Также в плюсах высокая производительность и отсутствие единой точки отказа.

**Пример команды**: 
```
sh.shardCollection("db.products", { "_id" : "hashed" })
```

### Коллекция carts
**Шард-ключ**: ```{ "client_id" : "hashed" }```

**Стратегия**: Хэшированное шардирование

**Обоснование**:
- Ключ client_id обеспечивает быстрый доступ для операций добавления/удаления товаров в корзине.
- Хэшированное шардирование подходит, так как нагрузка распределена равномерно, что крайне важно в период акций. Также в плюсах высокая производительность и отсутствие единой точки отказа.

**Пример команды**: 
```
sh.shardCollection("db.carts", { "client_id" : "hashed" })
```

## Задание 8. Выявление и устранение «горячих» шардов

### 1. Набор метрик
1. Метрики нагрузки
- opcounters — количество операций в секунду. 
- latency — время выполнения команд.
- connections — активные соединения.

2. Метрики ресурсов
- CPU — загрузка процессора.
- RAM — использование памяти.
- queue — очереди операций.
- cache — эффективность кэша.

3. Метрики распределения данных
- chunk_size и chunk_count — распределение чанков.
- jumbo_chunks — неделимые блоки.

4. Сетевые метрики
- network — сетевая активность.

### 2. Механизмы автоматического перераспределения данных
1. Переход на хэшированное шардирование

Если текущая стратегия приводит к перегрузке, рекомендуется перейти на хэшированное распределение. Обоснование было указано в задании 7.

```
sh.shardCollection("db.products", { "_id" : "hashed" })
```

2. Оптимизация ключа шардирования  

Если используется диапазонное шардирование и текущий ключ { category: 1 } создает горячий шард, необходимо превратить ключ в составной { category: 1, _id: 1 }. Таким образом нагрузка будет распределена более равномерно.

```
sh.refineCollectionShardKey("db.products", { category: 1, _id: 1 });
```

3. Балансировщик нагрузки

Встроенный балансировщик MongoDB автоматически перемещает чанки с перегруженных шардов на менее нагруженные. Его можно полностью включать и отключать, также можно настроить время работы по расписанию.

```
sh.getBalancerState();
sh.startBalancer();

db.settings.update(
    { _id: "balancer" },
    { $set: { activeWindow : { start : "01:00", stop : "05:00" } } },
    { upsert: true }
);
```

4. Геошардинг

Геошардинг можно комбинировать с актуальной стратегией шардирования. Так данные распределятся более равномерно. 
```
// Создание зон для разных шардов
sh.addShardToZone("shard1", "USA")
sh.addShardToZone("shard2", "EUROPE") 
sh.addShardToZone("shard3", "ASIA")

// Привязываем диапазон категории к зоне:
sh.updateZoneKeyRange(
    "shop.products",
    { category: "Electronics", _id: MinKey },
    { category: "Electronics", _id: MaxKey },
    "USA"
);
```

## Задание 10. Миграция на Cassandra: модель данных, стратегии репликации и шардирования

### 1. Обоснование применения Cassandra
Части данных интернет-магазина, критически важные с точки зрения целостности и скорости обработки: 
- Корзины — данные требуют высокой скорости записи и частых обновлений. Cassandra позволяет эффективно обрабатывать большие объемы записей с минимальной задержкой. Горизонтальное масштабирование Cassandra позволяет легко увеличить ресурсы системы при увеличении данных.
- История заказов — данные требуют минимальной задержки при чтении. Cassandra обеспечивает быстрое чтение данных. Геораспределенность Cassandra повышает высокую доступность данных и отказоустойчивость.
- Пользовательские сессии — данные требуют минимальной задержки при чтении и записи. Cassandra обеспечивает быструю запись и чтение данных. Репликация данных Cassandra повышает отказоустойчивость.

### 2. Концептуальная модель

1. carts:
- Partition key: client_id  
- Clustering key: created_at
- Обоснование: partition key client_id позволяет эффективно распределить данные по узлам Cassandra, обеспечивая быстрый доступ к этим данным. Кластерный ключ created_at обеспечит последовательный доступ к данным и поможет извлекать актуальную информацию (последнюю корзину).
- Пример создания таблицы в Cassandra:
```
CREATE TABLE carts (
    cart_id UUID,
    user_id UUID,
    session_id UUID,
    client_id UUID,
    created_at TIMESTAMP,
    status TEXT,
    item_id UUID,
    quantity DECIMAL,
    updated_at TIMESTAMP,
    expires_at TIMESTAMP,
    PRIMARY KEY (client_id, created_at, cart_id, item_id)
) WITH CLUSTERING ORDER BY (created_at DESC);
```

2. order_history:
- Partition key: client_id 
- Clustering key: order_id, created_at
- Обоснование: partition key client_id позволяет эффективно распределить данные по узлам Cassandra, обеспечивая быстрый доступ к этим данным. Кластерный ключ order_id и created_at позволяет сортировать заказы по времени их создания, обеспечивая быстрый доступ к этим данным.
- Пример создания таблицы в Cassandra:
```
CREATE TABLE order_history (
    client_id UUID,
    order_id UUID,
    created_at TIMESTAMP,
    status TEXT,
    total_amount DECIMAL,
    items LIST<TEXT>,
    PRIMARY KEY (client_id, order_id, created_at)
) WITH CLUSTERING ORDER BY (order_id DESC, created_at DESC);

```

3. user_sessions:
- Partition key: user_id
- Clustering key: session_id
- Обоснование:  partition key user_id позволяет эффективно распределить данные по узлам Cassandra, обеспечивая быстрый доступ к этим данным. Кластерный ключ session_id позволяет хранить несколько сессий пользователя, сортировать их и быстро извлекать данные. 
- Пример создания таблицы в Cassandra:
```
CREATE TABLE user_sessions (
    user_id UUID,
    session_id UUID,
    created_at TIMESTAMP,
    last_accessed_at TIMESTAMP,
    status TEXT,
    PRIMARY KEY (user_id, session_id)
);

```

### 3. Стратегии целостности данных

1. Hinted Handoff:
- Применение: сильно повышает доступность записи. Клиент не ждёт восстановления всех реплик ― достаточного подтверждения от доступных узлов. Позволяет быстро устранить кратковременную несогласованность после недолгих сбоев. Реплика догоняет пропущенные записи практически сразу при восстановлении связи. 
- Сущности: Корзины, Пользовательские сессии
- Обоснование: 
    - Данные о корзинах меняются очень часто и требуют высокой доступности записи для корректной работы системы, особенно в условиях высокой нагрузки. Hinted Handoff гарантирует, что пропущенные изменения быстро догоняют в случае восстановления узла.
    - Сессии пользователей должны быть записаны и доступны с минимальной задержкой, даже в случае сбоя одного из узлов. Hinted Handoff поможет обеспечить высокую доступность и быструю синхронизацию данных с восстановленными репликами, что критично для бесперебойной работы сайта и взаимодействия с пользователем.

2. Read Repair:
- Применение: полезен для часто читаемых данных. Они быстро становятся согласованными, так как любое чтение обнаружит и устранит расхождения.
- Сущности: Корзины, Пользовательские сессии
- Обоснование: 
    - Данные о корзинах меняются очень часто и требуют высокой доступности записи для корректной работы системы, особенно в условиях высокой нагрузки. Read Repair автоматически исправляет расхождения при каждом чтении данных, минимизируя несогласованность.
    - Сессии пользователей должны быть записаны и доступны с минимальной задержкой, даже в случае сбоя одного из узлов. Read Repair автоматически исправляет расхождения при каждом чтении данных, минимизируя несогласованность.

3. Anti-Entropy Repair:
- Применение: полноценная сверка данных между репликами, которая выполняется администратором вручную или по расписанию, чтобы устранить накопившиеся расхождения, которые не были исправлены хинтами и чтениями.
- Сущности: История заказов
- Обоснование: 
    - История заказов: Данные обновляются значительно реже по сравнению с корзинами или сессиями, поэтому расхождения между репликами не так критичны для работы системы в реальном времени. Anti-Entropy Repair устраняет накопившиеся расхождения между репликами на основе сверки данных и синхронизирует их в фоновом режиме.
